## Dimensions

### accessibility-baseline — CONFIRMED

**Rule:** Every report-viewer HTML asset (plugins/*/assets/*-viewer.html) must encode status/category information through more than color alone — a visible-without-interaction legend element (class="legend") or an explanatory note (e.g. class="note") pairing each color with an icon or text label — because tokens.css's CIEDE2000 deuteranopia/protanopia simulation found --cat-1/--cat-3 (and --status-good/--status-bad) too close under color-vision deficiency to be distinguishable by hue alone.

**Source:** `analyzed`

**Evidence:** tools/design-tokens/tokens.css:59-64 (measured CIEDE2000 dE00 5.69 deutan/5.30 protan for --cat-1/--cat-3, mandating "never color alone, always pair with an icon or a label"); enforced as rule R4 in docs/plugin-authoring/references/report-viewer-standard.md:88-108 and mechanically checked in CI by scripts/ci/check_viewer_conformance.py:188-193 (LEGEND_RE / class="legend" or note-element check over static markup, wired into .github/workflows/plugin-checks.yml per report-viewer-standard.md:216-218); documented violations at plugins/confab/assets/burndown-viewer.html:61-62 (defines .legend/.swatch, uses neither) and plugins/self-assess/assets/stage-map-viewer.html:174-178,408-410 (color meaning revealed only after click).

**Verification verdict:** `confirmed`

**Verification note:** Re-derived independently and the core evidentiary chain checks out. tools/design-tokens/tokens.css:58-64 does state, verbatim, "the closest pair under CVD simulation... falls under the same mandate as --status-good/--status-bad below: never color alone, always pair with an icon or a label," with dE00 5.69/5.30 for --cat-1/--cat-3 exactly as cited. docs/plugin-authoring/references/report-viewer-standard.md:88-108 contains a real "R4 — Colour is never the only channel" section quoting that same mandate and requiring a legend visible without interaction. scripts/ci/check_viewer_conformance.py:53-54,188-193 genuinely implements LEGEND_RE/NOTE_RE checks against class="legend" or class="note" in static markup, and .github/workflows/plugin-checks.yml:119-128 wires that script into CI; although the step itself uses continue-on-error: true, the aggregation job at lines 246 and 258 (`steps.viewer_conformance.outcome == 'failure' ... run: exit 1`) does turn a failing check into an overall CI failure, so the mechanical-enforcement claim is accurate, not just a step that silently passes. sourceMode "analyzed" is honest and the rule's phrasing (class="legend" or a class="note" element) tracks the actual CI regex closely enough to be mechanically re-testable later.

One inaccuracy worth flagging (not disqualifying): the candidate's "documented violations" citations (plugins/confab/assets/burndown-viewer.html:61-62 and plugins/self-assess/assets/stage-map-viewer.html:174-178,408-410) are stale. I read both files as they exist now: burndown-viewer.html has a fully wired `<ul class="legend">` at line 149 with `.swatch`/`.glyph`/`.name` spans explaining open/closed/escalated, and stage-map-viewer.html has a static `<ul class="legend" id="legend">` at line 107 plus an explicit "R4: a legend a reader gets without clicking anything" comment at line 41 — both already comply with R4 rather than violating it. That text was copied verbatim from report-viewer-standard.md's own (now outdated) violation list rather than re-verified against current file contents, so it overstates present-day non-compliance. It doesn't undermine the rule itself, which is real, current, and enforced — but the "documented violations" evidence should be corrected or dropped rather than cited as current fact.

Rule is concrete and checkable: a later audit can mechanically grep any plugins/*/assets/*-viewer.html for class="legend" or class="note" in static markup (or simply re-run scripts/ci/check_viewer_conformance.py), matching exactly what's proposed.

### color-and-contrast — CONFIRMED

**Rule:** Any color token used for text or a standalone chart mark must meet the WCAG 2.1 contrast thresholds measured and documented in tools/design-tokens/tokens.css (4.5:1 against --bg for text, 3:1 for marks) — meaning the *-deep steps (2.07–3.17:1, with only --samaria-deep at 3.17:1 as a mark-eligible exception) may be used solely as fills/borders, never as text or a lone chart-mark color — and any two categorical colors that are perceptually close under CVD simulation (per tokens.css, --cat-1/--cat-3 at dE00 5.69 deutan/5.30 protan) must never be the only channel distinguishing them; pair with an icon or label.

**Source:** `analyzed`

**Evidence:** tools/design-tokens/tokens.css:36-64 (measured WCAG contrast table and the CIEDE2000/never-color-alone mandate); reinforced by docs/plugin-authoring/references/report-viewer-standard.md:88-108 (rule R4, citing two live violations at plugins/confab/assets/burndown-viewer.html:61-62,280 and plugins/self-assess/assets/stage-map-viewer.html:174-178,408-410)

**Verification verdict:** `confirmed`

**Verification note:** Re-derived independently and the core claim holds. tools/design-tokens/tokens.css:36-64 (read directly) states exactly the numbers the rule cites: WCAG 2.1 (4.5:1 text / 3:1 marks) against --bg #0a0d10, the *-deep steps at 2.07-3.17:1 with --samaria-deep singled out at 3.17:1 as the one deep step that clears 3:1 (but is still declared fill/border-only "by role"), and the --cat-1/--cat-3 pair at CIEDE2000 5.69 deutan / 5.30 protan under the explicit "never color alone, always pair with an icon or a label" mandate — all verbatim matches, not paraphrase drift. A cross-repo grep of every *-deep token usage (plugins/lehre/assets/doctrine-viewer.html, plugins/andon/assets/board-viewer.html, etc.) shows them used only as border/outline/background — consistent with the rule, not contradicting it. The rule is concrete and mechanically checkable: a later auditor can grep for *-deep tokens applied to `color`/text-fill or standalone-mark properties, and check cat-1/cat-3 co-occurrence for an accompanying icon/label.

One flaw in the candidate's secondary evidence, worth correcting: it cites docs/plugin-authoring/references/report-viewer-standard.md:88-108's claim of 'two live violations' (burndown-viewer.html and stage-map-viewer.html) as reinforcement. I checked both files directly and neither violation is live anymore — plugins/confab/assets/burndown-viewer.html now defines `.legend`/`.swatch` at lines 82-94 AND renders it unconditionally at lines 149-153 (not unused, contradicting the doc's claim it 'uses neither'), and plugins/self-assess/assets/stage-map-viewer.html has an always-visible `#legendpanel` at lines 105-114, not a click-only sidebar badge. The report-viewer-standard.md text itself is stale relative to current code; the candidate faithfully quoted that doc but did not verify the underlying files still exhibit the violation, so that reinforcing half of 'evidence' does not currently hold. This does not undermine the rule's grounding, since the primary tokens.css citation is sufficient and accurate on its own, but the reinforcing citation should be dropped or updated rather than presented as current fact.

### spacing-and-layout-grid — NEEDS REVISION

**Rule:** Every margin/padding/gap value in project CSS must be a member of the established spacing scale for its file's domain — 4/8/12/16/24/32/48/64/96px (the `--wk-space-*` tokens) in `docs/.vitepress/theme/werkstoff.css`, or 4/8/12/16/20px (the `--space-*` tokens) in plugin viewer assets governed by `tools/design-tokens/tokens.css` — and any off-scale pixel literal used for spacing is a bug to be fixed, not a new convention.

**Source:** `analyzed`

**Evidence:** docs/.vitepress/theme/werkstoff.css:108-134 (defines --wk-space-1..24 = 4/8/12/16/24/32/48/64/96px with the explicit comment "Every value below is a member; a value that is not a member is a bug"); tools/design-tokens/tokens.css:148-153 (parallel --space-1..5 = 4/8/12/16/20px scale, comment "derived from values already in use")

**Note:** Adoption is real but incomplete: plugins/self-assess/assets/stage-map-viewer.html:35,70,79 and plugins/andon/assets/board-viewer.html mix `var(--space-N)` with off-scale literals (e.g. 18px, 14px 16px, 6px) alongside correct token usage, and plugins/compass/assets/branch-comparison-viewer.html:20 shows the scale already being applied and documented inline (citing report-viewer-standard.md's S1) after a prior fix. The scale itself is a deliberate, well-reasoned convention (not scaffolded), just not yet fully enforced everywhere it applies.

**Verification verdict:** `revise`

**Verification note:** The rule itself and its primary evidence are sound and the rule is concrete/checkable. I independently confirmed both token scales exactly as cited: docs/.vitepress/theme/werkstoff.css:126-134 defines --wk-space-1..24 = 4/8/12/16/24/32/48/64/96px with the explicit "a value that is not a member is a bug" comment (line 124-125), and tools/design-tokens/tokens.css:149-153 defines --space-1..5 = 4/8/12/16/20px "derived from values already in use." I also confirmed the two-domain split is exhaustive: 8 plugin viewer HTML files (andon, confab, self-assess, lehre, cupertino, compass, codebase-consistency, cli-scaffold) each inject a vendored plugins/*/assets/tokens.css copy of tools/design-tokens/tokens.css, and docs/.vitepress/theme/werkstoff.css is the only other CSS source of hand-authored spacing tokens in the repo — no third undocumented scale exists. This is a genuine, deliberate, analyzed convention, not scaffolded.

However, the candidate's supporting "note" citation is inaccurate and should be corrected before this is accepted as-is. It claims "plugins/self-assess/assets/stage-map-viewer.html:35,70,79 ... e.g. 18px, 14px 16px, 6px" — but I read that file directly and lines 35/70/79 actually contain "border-radius: 8px; padding: 10px 12px;", "margin: 12px 0 4px;", and "margin-right: 4px;" respectively; none of those match the quoted example values. The values 18px, 14px 16px do appear, verbatim, at the *same line numbers* (35, 70) but in a different file: plugins/andon/assets/board-viewer.html ("padding: 18px;" at line 35, "padding: 14px 16px;" at line 70, "padding: 12px 18px;" at line 79). This looks like evidence from two files got merged/misattributed under one citation — a real citation error, not merely imprecise. That said, the underlying substantive claim (incomplete adoption / off-scale drift in viewer CSS) is independently true: I found additional unflagged violations the note missed entirely, e.g. plugins/self-assess/assets/stage-map-viewer.html:35 itself ("padding: 10px 12px" — 10px is off-scale) and plugins/codebase-consistency/assets/matrix-viewer.html (6px, 10px, 18px, 14px literals at lines 54, 63, 97, 127, 167, 193, 208 etc.), so the drift is real and broader than what was cited, just cited against the wrong file/line pairing.

Recommend: keep the rule and its primary evidence (werkstoff.css:108-134, tokens.css:148-153) as-is — those are honestly analyzed and the rule is mechanically auditable — but fix the note's citation to correctly attribute the 18px/14px-16px examples to plugins/andon/assets/board-viewer.html:35,70,79 rather than self-assess/stage-map-viewer.html, and optionally broaden it to mention codebase-consistency/matrix-viewer.html and self-assess/stage-map-viewer.html's own genuine (differently-lined) violations.

### typography-system — CONFIRMED

**Rule:** Every plugin's HTML report viewer must set its base font-family, font-size, and line-height exclusively via the shared design tokens (`var(--font-sans)`, `var(--font-size-base)`, `var(--line-height-base)`, defined once in tools/design-tokens/tokens.css:144-146 and vendored into every plugins/*/assets/tokens.css) rather than a hardcoded literal font stack/size/line-height.

**Source:** `analyzed`

**Evidence:** tools/design-tokens/tokens.css:144-146 defines --font-sans/--font-size-base/--line-height-base as the single typography source vendored into every plugin's assets/tokens.css; 7 of 8 report viewers consume these instead of hardcoding — plugins/andon/assets/board-viewer.html:15-17, plugins/confab/assets/burndown-viewer.html (font-size: var(--font-size-base) at line 16), plugins/cupertino/assets/review-flow-viewer.html:15-17, plugins/lehre/assets/doctrine-viewer.html:13, plugins/codebase-consistency/assets/matrix-viewer.html:15-16, plugins/cli-scaffold/assets/architecture-tree-viewer.html:26 (`font: var(--font-size-base)/var(--line-height-base) var(--font-sans)`), plugins/compass/assets/branch-comparison-viewer.html:13. The one holdout confirms this is a real, checkable convention rather than incidental: plugins/self-assess/assets/stage-map-viewer.html:22 currently hardcodes `font: 14px/1.45 system-ui, sans-serif` on the html/body rule instead of the token trio, a live drift instance this rule would catch.

**Verification verdict:** `confirmed`

**Verification note:** Re-derived independently: tools/design-tokens/tokens.css:144-146 does define --font-sans, --font-size-base (14px), --line-height-base (1.45) exactly as claimed, and all 8 plugins/*/assets/tokens.css vendor the same trio at the same lines (spot-checked self-assess). All cited file:line evidence for the 7 conforming viewers (andon board-viewer.html:15-17, confab burndown-viewer.html:16, cupertino review-flow-viewer.html:15-17, lehre doctrine-viewer.html:13, codebase-consistency matrix-viewer.html:15-16, cli-scaffold architecture-tree-viewer.html:26, compass branch-comparison-viewer.html:13) checks out verbatim, and the holdout citation (self-assess/assets/stage-map-viewer.html:22, `font: 14px/1.45 system-ui, sans-serif`) is real and exactly as described -- a genuine live drift instance that makes this a real, checkable, non-incidental convention rather than fabricated pattern-matching. Two minor wrinkles that don't undermine the sourceMode claim: confab's base rule doesn't visibly set line-height via any mechanism (candidate didn't claim it did, only cited font-size), and codebase-consistency's matrix-viewer.html base rule likewise sets font-family/font-size via tokens but has no line-height property at all on that rule (an omission, not a hardcoded literal) -- meaning it doesn't fully satisfy the rule's literal 'must set...line-height...via tokens' requirement despite being counted among the 7 compliant viewers. This is a small inaccuracy in the summary count, not invented evidence, and doesn't change the verdict. The rule is concrete and mechanically checkable: for each plugins/*/assets/*-viewer.html, grep the base html/body selector for a literal font-family/font-size/line-height value versus var(--font-sans)/var(--font-size-base)/var(--line-height-base).

### interaction-and-motion — CONFIRMED

**Rule:** Any CSS `transition` declared in a `plugins/*/assets/*-viewer.html` report must use the `var(--transition-fast)` (or `var(--transition-base)`) duration token from `tools/design-tokens/tokens.css` — never a hardcoded duration literal (e.g. `150ms`, `0.2s`) — so all hover/focus motion timing stays centrally tunable through the one vendored tokens file.

**Source:** `analyzed`

**Evidence:** tools/design-tokens/tokens.css:174-176 defines `--transition-fast: 120ms ease;` / `--transition-base: 200ms ease;` under a "Motion" section; every actual `transition:` declaration across the report viewers consumes `var(--transition-fast)` and none hardcodes a duration — plugins/andon/assets/board-viewer.html:102 (`transition: stroke var(--transition-fast);`), plugins/lehre/assets/doctrine-viewer.html:75,102,112, plugins/confab/assets/burndown-viewer.html:25. A grep for `transition:` followed by a literal `\d+m?s` value across plugins/*/assets/*.html returns zero matches, confirming no hardcoded-duration exceptions exist today.

**Verification verdict:** `confirmed`

**Verification note:** Verified independently. tools/design-tokens/tokens.css:174-176 has a "Motion" section defining `--transition-fast: 120ms ease;` and `--transition-base: 200ms ease;`. Grep across plugins/*/assets/*.html for `transition:` finds only var()-based declarations (plugins/lehre/assets/doctrine-viewer.html:75,102,112; plugins/andon/assets/board-viewer.html:102; plugins/confab/assets/burndown-viewer.html:25 — matches candidate's citations exactly), and a regex grep for a hardcoded duration literal following `transition:` (e.g. `\d+m?s`) returns zero matches, confirming no exceptions. Also confirmed the vendoring mechanism the rule relies on: each plugin carries its own assets/tokens.css copy (e.g. plugins/andon/assets/tokens.css, injected via plugins/andon/scripts/build_board_html.py:38-42 replacing a design-tokens marker), so 'centrally tunable through the one vendored tokens file' is an accurate description, not invented. sourceMode 'analyzed' is honest. The rule is concrete and mechanically checkable (grep any `transition:` in a report-viewer HTML for a literal duration vs. `var(--transition-fast|--transition-base)`). One minor note: `--transition-base` itself is currently unused by any viewer (only `--transition-fast` appears), but the rule only permits it as an alternative and doesn't misrepresent it as already in use, so this doesn't undermine the claim.

### empty-and-error-states — NEEDS REVISION

**Rule:** Every report-viewer HTML asset (plugins/*/assets/*-viewer.html) must, when its embedded data is missing or fails to parse, render a visible message naming the exact command to re-run to regenerate the data (not a blank page or silent no-op), then halt further rendering with a thrown error.

**Source:** `analyzed`

**Evidence:** docs/plugin-authoring/references/report-viewer-standard.md:172-175 states this as rule S4 ("Fail visibly ... a missing or unparseable input renders a 're-run X to regenerate' message, never a blank page"); confirmed live in all eight viewers, e.g. plugins/andon/assets/board-viewer.html:150-153 ("No board data found in this file.<br>Re-run <code>andon-status</code> to regenerate it." followed by throw new Error('no data')), plugins/cli-scaffold/assets/architecture-tree-viewer.html:109-111, plugins/codebase-consistency/assets/matrix-viewer.html:320-324, plugins/confab/assets/burndown-viewer.html:180-186, plugins/compass/assets/branch-comparison-viewer.html:114-119, and plugins/self-assess/assets/stage-map-viewer.html:143-144,171.

**Verification verdict:** `revise`

**Verification note:** The six cited file:line locations are real and accurately quoted: plugins/andon/assets/board-viewer.html:147-153, plugins/cli-scaffold/assets/architecture-tree-viewer.html:106-111, plugins/codebase-consistency/assets/matrix-viewer.html:317-324, plugins/confab/assets/burndown-viewer.html:177-186, plugins/compass/assets/branch-comparison-viewer.html:110-119, and plugins/self-assess/assets/stage-map-viewer.html:142-144/169-171 all do render a "no data found ... Re-run <command> to regenerate it" message and then `throw new Error(...)`. docs/plugin-authoring/references/report-viewer-standard.md:172-175 (S4) is also accurately quoted.

But the rule's own "every ... must" claim, and the candidate's added assertion "confirmed live in all eight viewers," do not hold up against the two viewers the candidate did not cite:

- plugins/cupertino/assets/review-flow-viewer.html:133-148 does not fail visibly at all — on missing/null `FLOW_DATA_RAW` it silently falls back to a fabricated demo dataset (`const FLOW = FLOW_DATA_RAW || {...9 hardcoded stages...}`) and only adds a subtitle note ("no data — template opened directly..."). No error is thrown, no "re-run X" command is named, and the page renders full fake content — exactly the "silent no-op" the candidate rule says must not happen.
- plugins/lehre/assets/doctrine-viewer.html:521-527 does show a visible message ("No doctrine data was injected into this template.") but does not name a re-run command, and does not throw — it just `return`s from the boot IIFE, so rendering halts by omission rather than by a thrown error.

So the standard doc's own S4 claim ("All eight already do this correctly") is stale/inaccurate, and the candidate propagated that error rather than independently checking all eight assets before writing "confirmed live in all eight viewers." The rule itself is concrete and mechanically checkable (visible message naming an exact re-run command + thrown error) — that part is fine — but as an "analyzed" claim about current universal conformance it is dishonest for 2 of 8 files, and treating it as already-true would let a drift audit wrongly pass cupertino/lehre or wrongly flag the whole repo as already compliant. Recommend either narrowing the evidence/note to the 6 conforming viewers and flagging cupertino/lehre as known non-conformant (a fix target), or explicitly stating the rule is aspirational for those two.
